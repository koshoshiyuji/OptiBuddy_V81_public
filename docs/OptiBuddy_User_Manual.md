# OptiBuddy ユーザーマニュアル (V8.5)

---

## 1. OptiBuddyとは

OptiBuddyは、**業務をDSL（Domain Specific Language）として定義すると、AIとソルバーが協働して最適スケジュールや構成を決定するアプリケーションを提供する、汎用業務最適化プラットフォーム**です。

特定業界に固定された専用ツールではなく、「タスク・リソース・制約・目的関数」という共通構造を基盤に、業務ごとの追加ルールをAIが自動設計することで、コンテナターミナルの荷役計画からイベントスタッフ配置まで、幅広い業務領域に対応します。

### ユーザーがすることは、ほぼ「話す」だけ

OptiBuddyの最大の特徴は、**ユーザーが専門知識なしに業務最適化アプリを手に入れられる**ことです。

- 業務を登録するとき ── ヒアリングシートに自社の言葉で記入する
- 結果を確認するとき ── タブを眺め、気になる点をAIチャットに日本語で質問する
- 問題を解決するとき ── AIの提案に「適用する」か「やめる」かを答える

数理モデルの構築・コーディング・制約の定式化はすべてAIが担います。ユーザーは業務の現実を言葉で伝えるだけです。

## 2. アプリ構築の考え方

### 2-1. 6つの基底モデル

OptiBuddyで構築できる最適化アプリはすべて、数理的に確立された以下の基底問題のいずれかをベースとしています。ユーザーがこれを意識する必要はありません。AIがヒアリング内容から最適なベースを自動判定します。

| 基底問題 | 典型的な業務適用例 | OptiBuddyドメイン |
|---|---|---|
| RCPSP（資源制約付きスケジューリング） | コンテナ荷役・工程計画・工事現場管理 | YardPlanning |
| スタッフ割り当て最適化 | イベント運営・シフト管理・店舗配置 | EventStaffing |
| CFLP（容量制約付き施設配置） | 拠点選定・DC配置・ゴーストキッチン展開 | GhostKitchen |
| ナップサック問題（多次元選択） | 投資判断・プロジェクトポートフォリオ | ProjectPlanner |
| CVRP（容量制約付き車両ルーティング） | 配送ルート最適化・送迎バス運行 | CapacitatedVehicleRoutingProblem |
| ビンパッキング | クラウドサーバー配置・コンテナ積載 | BinPacking |

### 2-2. extensionsとは（概念のみ）

同じ基底問題でも、業務が異なれば制約が異なります。OptiBuddyはこの差異を **extensions（拡張モジュール）** として内部管理しています。「積み重ね順序を守る」「シフト時間帯内でのみ作業する」「Reefer区画にのみ冷凍コンテナを置く」といったルールが個別のブロックとして組み合わさり、業務固有の制約モデルを形成します。

ユーザーがextensionsを直接編集することは通常ありません。業務登録時にAIが内容を解析し、必要なextensionsを自動選択・生成します。「こういうルールが必要だ」と気づいたときは、AIチャットで自然言語で伝えるだけです。

## 4. 業務登録（新規ドメイン追加）

### 4-1. 概要

ホーム画面の **「✨ 新規業務登録」** から開始します。ヒアリングシートに業務内容を記入すると、AIがコードを自動生成・登録し、新しいドメインが利用可能になります。**ユーザーがコードを書く必要は一切ありません。**

### 4-2. ヒアリングシートの記入

以下の項目を **自社の言葉で** 記入してください。専門用語・数式は不要です。記入量の目安はA4用紙1〜2枚程度です。

| 項目 | 必須 | 記入のポイント |
|---|---|---|
| **業務の概要** | ◎ | 「何を」「どこに / 誰に」割り当てるか、2〜3行で |
| **割り当ての構造** | ◎ | 割り当てられる側と割り当て先、それぞれのおおよその個数 |
| **最適化の目的** | ◎ | 最小化 / 最大化したいもの（例：トラック台数・人件費）と優先順位 |
| **絶対に守るルール** | ◎ | 破れないハード制約（例：積載量超過禁止・勤務時間8時間以内） |
| **できれば守りたいルール** | 任意 | ソフト制約（例：なるべく同じドライバーにまとめたい） |
| **解けない場合の対応** | 任意 | 制約を緩和して再挑戦したい / AIに緩和案を提案させたい |
| **画面で確認したい情報** | 任意 | 使用台数・稼働率・未割り当て一覧など |
| **データの補足** | 任意 | 割り当て先・対象の重要属性 |
| **特殊な要件** | 任意 | グループ分散・セキュリティ隔離・時間順序など |

### 4-3. 自動登録のしくみ

ヒアリング内容はAIが3段階で処理します。

```
Stage 1a：問題分類
  ヒアリング内容をAIが解析
  → 既存ドメインの変種か / 完全新規ドメインか を判定

Stage 1b（既存ドメインの変種の場合）：
  既存スキーマをベースにシナリオJSONを自動生成・DB登録
  → コード生成なし。数十秒で完了

Stage 2（完全新規ドメインの場合）：
  Solver / Converter / UIコンポーネント / シナリオJSON を自動生成
  → ファイル書き込み + DB登録 → 数分で新ドメインが有効化
```

### 4-4. 登録後の確認

登録完了後、シナリオ選択画面に新しいカードが表示されます。

- [ ] カードが表示されている
- [ ] クリックして最適化が実行される
- [ ] KPI・Issuesが正しく表示される
- [ ] Infeasibleシナリオで「解なし」モードに遷移する

## 5. シナリオ追加

既存ドメインに対して、条件・規模の異なるシナリオを追加できます。ホーム画面の **「📋 シナリオ追加」** から開始します。

**手順**

1. 対象ドメインを選択
2. 「こういうケースを試したい」を自然言語で入力
3. AIが既存DSLスキーマを参照してシナリオJSONを自動生成
4. プレビューを確認して「登録」

シナリオは以下の3種類を用意しておくことを推奨します。

| 種類 | 内容 | 用途 |
|---|---|---|
| **Baseline（標準）** | 通常規模・全制約を満たす | 正常動作確認 |
| **Tight（タイト）** | ギリギリ解が見つかる条件 | ストレステスト |
| **Infeasible（解なし）** | 制約上解が存在しない条件 | Infeasible処理確認 |

## 6. 最適化の実行と結果確認

### 6-1. 実行方法

シナリオカードをクリック、またはスタジオ画面の **「▶ RUN GLOBAL OPTIMIZATION」** ボタンをクリックします。

### 6-2. 結果の確認タブ

業務ドメインによって表示されるタブが異なります。

| タブ | 表示条件 | 内容 |
|---|---|---|
| **Overview** | 常に表示 | KPIサマリー・複数解選択・イシュー概要 |
| **Issues** | 常に表示 | 検出された問題一覧と対応操作 |
| **Timeline** | YardPlanning | 詳細ガントチャート・タイムスライダー |
| **Yard / Vessel** | YardPlanning | ヤード・船のビジュアル表示 |
| **Staff / Task** | EventStaffing | スタッフ別割り当て・人件費 |
| **Kitchen** | GhostKitchen | 開設・閉鎖拠点一覧とKPI |
| **Projects** | ProjectPlanner | 採択・非採択プロジェクト一覧 |
| **CVRP** | CVRP | 配送ルートマップとKPI |
| **Bin Packing** | BinPacking | ビン（サーバー等）への割り当て結果 |

### 6-3. 複数解の選択

ソルバーは最適化方針の異なる複数プランを生成することがあります。Overviewタブ上部の **SOLUTIONセレクター** で切り替えて比較できます。

## 7. イシューへの対応と再最適化

### 7-1. イシューの種類

最適化後にルール違反や改善可能な点が検出されると、Issuesタブに一覧表示されます。

| 深刻度 | 色 | 内容 |
|---|---|---|
| **CRITICAL** | 赤 | 絶対に解決が必要な制約違反（積み順矛盾・人数不足など） |
| **WARNING** | 橙 | 対処を推奨する問題（重量逆転・シフト外作業など） |
| **INFO** | 青 | 情報提供（未割り当てスタッフなど） |

### 7-2. FIX / ACCEPT アクション

各イシューに対して2つのアクションを選べます。

| ボタン | 内容 |
|---|---|
| **FIX（修正する）** | このイシューに対応する制約をシステムが自動緩和し、再最適化の対象とする |
| **ACCEPT（許容する）** | 問題を承知の上でそのまま許容する（以後のリストから除外） |

FIX / ACCEPT を選択後、「RUN GLOBAL OPTIMIZATION」で再最適化します。Issues タブ上部の「全てFIX」「全てACCEPT」で一括処理も可能です。

### 7-3. 再最適化の2つの経路とInfeasible

OptiBuddyには再最適化のアプローチが2つあります。これらは目的が異なり、どちらを使っても **再び Infeasible になる可能性はゼロではありません。**

---

**① Issues / AIチャット経由の制約緩和**

現在の解で検出されたイシューをFIXするか、AIに改善提案を求めて適用するアプローチです。

```
イシューを確認 / AIに質問
  ↓
FIXアクション選択 または AI提案を「適用して再最適化」
  ↓
対象の制約が緩和された状態でソルバーが再実行
  ↓
新しい解（改善されていることが多いが、他のイシューが浮上することもある）
```

このアプローチは「解は出ているが、内容に問題がある」場合に使います。制約緩和の幅が小さいと依然として別のイシューが発生します。また、複数の制約が相互に競合している場合、一方を緩和しても他方が原因でInfeasibleになることがあります。

---

**② 制約構造の見直し（Infeasible / 根本的な見直しが必要な場合）**

そもそも現在の制約設定では解が存在しないか、出力結果が業務実態と大きくかけ離れている場合は、AIチャットで制約構造ごと見直します。

```
「なぜ解が見つからないか」をAIチャットで聞く
  ↓
AIが制約の矛盾箇所・緩和候補を診断して提案
  ↓
提案内容を確認し「適用して再最適化」を選択
  ↓
DSLが更新されてソルバーが再実行
  ↓
解が見つかれば完了。依然Infeasibleなら再度AIと対話
```

このアプローチは「ヒアリングで定義したルール自体に矛盾がある」「現実的に不可能なスケジュールを要求している」場合に有効です。それでも解が出ない場合は、業務上の前提（リソース数・時間枠・容量上限など）を見直す必要があります。AIは「この制約を外せば解ける」という診断を具体的に示しますので、最終的にどの制約を緩和するかはユーザーが判断します。

---

**GhostKitchenドメインの場合**

GhostKitchenではカバー率不足や解なしの際に **パラメータ調整パネル** が表示されます。最大開設拠点数・最低カバー率目標・ソルブ時間上限を手動で変更して再最適化できます。変更前後の値が並べて表示されるため、差分を確認してから「この設定で再最適化」を適用します。

## 8. OptiBuddy AIチャット

### 8-1. OptiBuddyにおけるAIの役割

OptiBuddyでは、AIは単なる「質問回答ツール」ではありません。**最適化の全工程においてAIが中心的な役割を担っています。**

| フェーズ | AIが担うこと |
|---|---|
| 業務登録 | ヒアリング内容の解析、問題分類、制約モデルの自動設計、コード生成 |
| 最適化結果の解釈 | イシューの原因診断、改善案の提案 |
| 再最適化 | DSLの自動修正と再実行 |
| Q&A | 結果の説明、仮説検証（「台数を増やしたら？」など） |

ユーザーとAIのインタラクションは基本的に **自然文のQ&A** です。専門用語を覚える必要はありません。

### 8-2. 使い方

画面右下の **「💬」** ボタンをクリックするとAIパネルが開きます。現在の最適化結果・業務DSL・イシュー情報をすべてAIが把握した状態で回答します。

1. テキストエリアに質問を日本語で入力
2. 「送信」ボタンをクリック（または `Cmd+Enter`）
3. AIが回答
4. 改善提案がある場合、**「✅ 適用して再最適化」** ボタンが表示される
5. ボタンをクリックするとDSLが自動更新され、ソルバーが再実行される

### 8-3. 質問の例

**原因を聞く**
- 「GC-1に空白時間が多いのはなぜ？」
- 「なぜmakespanがこんなに長い？」
- 「このイシューが解消できない理由は？」

**改善案を聞く**
- 「どの制約を緩和すれば解ける？」
- 「クレーンを1台増やすと何分短縮できる？」
- 「今のシナリオで一番ボトルネックになっているのはどこ？」

**変更を依頼する**
- 「積載量を10%増やして再最適化してほしい」
- 「シフトの終了時刻を1時間延ばして試算したい」
- 「このルールが現実的でないので外してほしい」

### 8-4. 注意点

AIの改善提案は「✅ 適用して再最適化」ボタンを押した場合のみ反映されます。ボタンを押さない限り、現在の最適化結果は変更されません。適用後は元に戻せないため、重要な変更前にはDSLを手元に保存しておくことを推奨します。

## 9. サンプル業務ドメインの概要

標準搭載されているドメインの概要です。各ドメインの詳細な制約・操作はAIチャットで確認できます。

| ドメイン | ベース問題 | 最適化の目的 |
|---|---|---|
| **YardPlanning** | RCPSP | コンテナ荷役クレーン作業のMakespan最小化 |
| **EventStaffing** | スタッフ割り当て | 総人件費最小化・スタッフ希望充足 |
| **GhostKitchen** | CFLP | 拠点固定費最小化・需要カバー率確保 |
| **ProjectPlanner** | ナップサック | 予算・人員・期間制約内のROI最大化 |
| **CapacitatedVehicleRoutingProblem** | CVRP | 積載量・時間窓制約つき配送ルート最適化 |
| **BinPacking** | ビンパッキング | CPU・メモリ制約つきサーバー配置最適化 |

各ドメインにはBaseline（標準）・Tight（タイト）・Infeasible（解なし）の3シナリオが用意されており、動作確認・ストレステストに使用できます。

## 10. カスタムUIを作りたい場合

OptiBuddyのUIはプロトタイピングと業務検証に最適化されています。本番システムへの組み込みや、自社デザインシステムに合わせた独自UIを構築したい場合は、**OptiBuddyをバックエンドのAPIエンジンとして利用し、フロントエンドは独自開発する**アーキテクチャを推奨します。

```
OptiBuddy（バックエンド）
  POST /api/domain/run    ← 業務DSLを送信
  POST /baseline          ← 最適化実行
  GET  /scenarios         ← シナリオ一覧取得
     ↓
最適化結果（JSON）
     ↓
自社フロントエンド（React / Vue / Next.js など）
  ← 結果を受け取り、自社のデザイン・UXで表示
```

OptiBuddyが返すUI DSL（`ui_dsl`）は、KPI・ルート・割り当て結果・イシュー情報を構造化されたJSONとして提供します。フロントエンド側では好きなチャートライブラリ・マップライブラリ・デザインシステムと組み合わせて自由にUIを構築できます。

この場合の最適化ロジック・制約モデル・AI診断はOptiBuddy側に完全に残るため、フロントエンドは表示に専念できます。

Overviewタブの **「EXPORT CSV」** ボタンから結果をダウンロードできます。

| カラム | 内容 |

| resource | 使用リソース |
| start_min | 作業開始時刻（分） |
| end_min | 作業終了時刻（分） |

| カラム | 内容 |
|---|---|

| severity | 深刻度（CRITICAL / WARNING / INFO） |
| title | イシュー内容 |
| status | 対応状況（UNRESOLVED / FIX / ACCEPT） |

## 12. よくある質問

**Q: 業務を登録するのにどのくらいの知識が必要ですか？**
A: 最適化の専門知識は不要です。「何を・誰に割り当てたいか」「守らなければならないルールは何か」「何を最小化/最大化したいか」を自社の言葉で書けば、AIが残りを担います。

**Q: 新規業務登録はどのくらいの時間がかかりますか？**
A: 既存ドメインに近い業務（「別の配送ルートを追加したい」など）は数十秒で完了します。完全新規ドメインはコード生成が入るため数分かかることがあります。

**Q: ガントチャートに大きな空白があります**
A: AIチャットで「なぜ○○に空白がある？」と入力してください。原因説明と改善提案を返します。

**Q: 制約を満たす解が見つからない（Infeasible）場合は？**
A: AIチャットで「なぜ解が見つからないか」を聞いてください。制約の矛盾箇所を診断し、具体的な緩和候補を提示します。それでも解が出ない場合は、業務上の前提（リソース数・時間枠・容量など）の見直しが必要です。

**Q: AIが提案した改善を適用したら別の問題が出ました**
A: 制約は相互に影響するため、一方を緩和すると別のイシューが浮上することがあります。再度AIチャットで状況を説明すると、次の緩和候補を提示します。完全に解消できない場合は業務要件自体の再検討が必要な可能性があります。

**Q: AIチャットの改善提案は自動で適用されますか？**
A: 「✅ 適用して再最適化」ボタンをクリックした場合のみ反映されます。ボタンを押さない限り、現在の最適化結果は変更されません。

**Q: OptiBuddyのUIではなく自社UIで結果を表示したい**
A: セクション10を参照してください。OptiBuddyをAPIエンジンとして使い、フロントエンドを独自開発するアーキテクチャを推奨しています。
